# V1.0.5 架构与业务契约

## 目标与边界

增强既有模块化单体，不引入第二套用户、账目、账户、预算或同步系统。账目原币金额、用户ID及幂等操作ID保持稳定。业务UI经Feature Store→Repository→LocalStateSession写本地，财务实体经SyncQueue→SyncCoordinator同步。

推荐采用共享口径＋现有模块增量扩展。逐页面补丁不能保证统计与预算一致；整体重写会危及已验收同步和历史数据，两者均不采用。

## 已验证的缺口

1. AccountDetailPage归档写`deletedAt`，AssetsRepository却仍发`upsert`，后端save_account又把deleted_at清空。归档与删除混淆且没有恢复字段/入口。
2. AssetsRepository.saveExchangeRate只写本地，没有账户快照队列操作。随后服务器账户状态可以覆盖本地转换；saveManualExchangeRate还尝试服务器已禁止的公共汇率写接口。
3. LedgerPage按当前数组倒序，未按发生日期排序；分类筛选不存在。
4. 统计已有按范围的分类/账户聚合，故不能宣称所有历史日均根因已证实；需回归验证月份选择、日期来源和分母。UI缺分类/账户下钻入口。
5. 预算数据库/客户端category_id实际必填，与Excel“可选”证据不符。保留实体，以保留标识`__total__`表示月度总额，独立于用户分类。
6. Auth只有用户名密码，没有可验证联系方式。用户选择恢复码：复用User和auth_version，高熵单次凭证，在当前密码验证后预先生成并保存哈希。

## 财务规则

- 发生日期字段`date/occurred_on`控制范围与排序；`occurred_at`只提供同日时间，创建/修改时间不改变归属月份。
- 原币amount、currency为事实；CNY使用原金额，外币只使用可靠cny_amount快照。未知换算明确计数，不当成真实0，也不自动用最新汇率重写历史账单。
- 转账不进入收入/支出/预算；软删除不进入实时统计；退款由既有income契约表示，单列收入，不猜测其原分类，也不从消费静默扣减。
- 总额预算消费等于同月全部有效可换算支出；分类预算为其子集。总额限额和分类限额不相加。
- 日均：历史完整周期用全部自然日；当前周期截至今日；未来周期分母0且日均0。只统计同一有效日期集合，展示未换算数量。
- 筛选条件保留分类/账户/收支/起止日/关键词。聚合与下钻使用同一过滤契约，分类“其他”需要明确其包含集合，不把其当单个category ID。
- 汇率快照按币种对独立，校验有限正数和日期；手动来源属用户实体快照，不能污染公共汇率。账户初始金额转换不改变原币金额、不重复乘上既有CNY值。

## 数据扩展与升级

服务端新增迁移`0003_v105_accounts`添加账户note/archived_at，并预留独立Auth恢复迁移。现存User/Account/Transaction ID、金额、版本不重建。Drift保存FinanceState JSON，新增可选字段默认兼容，无需重建SQLite表；建立旧JSON＋待同步队列重新打开测试。

归档字段独立于deleted_at，归档后隐藏于新记账账户选择，历史查询仍解析其名称。恢复清空archived_at，仍用账户upsert。旧deleted_at不擅自清空，因为无法判定旧用户删除意图。

跨端同步按实体保留server_version，新增修改经既有冲突处理。换算写账户快照必须与本地状态和队列同一串行事务构造，检查全部受影响调用方。公共汇率GET失败时返回缓存日期/来源/stale标记，无缓存502。客户端明确标出缓存，不把失败当刷新成功。

## 认证恢复

已登录用户输入当前密码生成高熵恢复码；服务端仅存哈希，明文仅在该次响应展示。未登录用户提供用户名、恢复码、新密码，事务内锁User，校验后消费恢复码并递增auth_version；旧登录令牌失效。失败信息一致，不暴露账号存在性，沿用限流。成功后要求常规登录，ID和财务数据不变。没有预先保存恢复码的旧用户不会被无凭证恢复。
